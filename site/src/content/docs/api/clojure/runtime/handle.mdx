(require '[toolnexus.agents.runtime :as rt])

(def h (rt/spawn runtime rt/root "writer"))   ; => "root/writer.1", a deterministic, parent-scoped id

(rt/handles runtime)     ; => tree-order snapshot, every handle under root

"A Handle is a live agent: a state machine (`idle → running → idle|suspended|closed`, and
`suspended → running` ONLY via the Answer to its pending Request), an inbox held as AGENT state
(never a language mailbox), a carved budget, and a deterministic parent-scoped id"
(`clojure/src/toolnexus/agents/runtime.cljc:10-13`). A `Handle` is what every
[`create-runtime`](/api/clojure/runtime/runtime/) verb operates on — `spawn` creates one, `wake`/
`wait`/`interrupt`/`close`/`resume` act on one by id, and `handles`/`inspect` are the read-only
windows onto its current state.

## The four states

- **`idle`** — alive, no turn in flight. A freshly spawned handle starts here; a handle that
  settles (with a `"done"`, `"incomplete"`, `"interrupted"`, or `"error"` result) returns here,
  never to `"closed"` on its own.
- **`running`** — a turn is in flight, admitted by `wake` through gate 1 (bounded inbox), gate 2
  (per-parent concurrency, FIFO-queued past the cap) and gate 3 (a tree-wide cap on LLM calls
  actually in flight).
- **`suspended`** — parked on a pending §10 `Request` (or a budget limit routed through
  `"suspend"`). The **only** way out is `resume` with the matching `Answer` — waking or posting to
  a suspended handle just buffers, it never moves the state.
- **`closed`** — torn down by `close`. Still queryable: `inspect` still answers, `wait` still
  returns the last recorded result, and a fresh handle may be `spawn`ned in its place from the same
  registry entry. Close ≠ loss.

## What `inspect` returns

`(rt/inspect runtime id)` is the detail view of one handle — `view` (`:id`, `:state`, `:tokens`,
`:inbox`) plus three extra fields (`clojure/src/toolnexus/agents/runtime.cljc:588-593`):

- **`:turns`** — `:turns-total`, the handle's lifetime turn count (grows across a `resume`, never
  resets).
- **`:pool-tokens`** — the token allowance this handle's OWN carved budget pool still holds. This
  is the handle's local carve, not the live ancestor-chain walk `spawn`/`wake` also check — see
  [`Budget`](/api/clojure/runtime/budgets/) for why the carve alone is not enough to catch a
  sibling's overspend.
- **`:pending`** — the §10 `Request` this handle is parked on, when `:state` is `"suspended"`;
  `nil` otherwise.

`(rt/handles runtime)` is the coarser, tree-order sibling: every handle under a given root (default
`rt/root`), each rendered through the same `view` — `:id`, `:state`, `:tokens`, `:inbox` — with no
`:turns`/`:pool-tokens`/`:pending`. Reach for `handles` to enumerate a tree or build a dashboard;
reach for `inspect` when you already have one id and want its full detail.

## When to use it

- **Branching on a handle's `:state`** after a verb call, e.g. deciding whether a `"suspended"`
  handle needs a host to answer its pending request, or a `"running"` one just needs a longer
  `wait`.
- **Building an observability view** — a dashboard listing every live sub-agent, its token spend,
  and its inbox depth, without touching any verb that would change state.
- **Confirming a handle survived `close`** — `inspect` on a closed handle still answers with its
  last state and result, which is exactly the guarantee that makes "close ≠ loss" true in practice.

## Why this and not the alternative

<Aside type="tip" title="A handle is an id you hold, not an object you pass around">
Other ports return a `Handle` object with its own methods (`handle.wait()`, `handle.close()` in
js/python/java/csharp). This port's `spawn` returns a plain **id string**, and every other verb
(`wake`, `wait`, `interrupt`, `close`, `inspect`) takes `runtime` and that id as separate
arguments. That is deliberate: "handles are capabilities — post and wake what you hold, wait only
on what you spawned" (`runtime.cljc:719-720`), and an id is trivially something you can hold in a
set, log, or pass across a boundary without smuggling a live reference to the runtime's internal
state along with it. `wait`'s own `:by` option enforces the capability rule at the verb level — a
handle waited on by anyone other than its actual spawner settles with an `"error"` result, never a
silent success.
</Aside>

## Examples

### 1. The smallest useful call — read one handle's state after spawning it

```clojure
(require '[toolnexus.agents.runtime :as rt])

(let [h (rt/spawn runtime rt/root "w")]
  (:state (rt/inspect runtime h)))   ; => "idle" — a fresh handle is idle, not running
```

### 2. The realistic case — watch a handle move through running to idle

```clojure
(let [h (rt/spawn runtime rt/root "w")]
  (rt/wake runtime h "go")
  (let [r (rt/wait runtime h)]
    (:status r))                    ; => "done"
  (:state (rt/inspect runtime h)))  ; => "idle" — a settled handle returns to idle, never "closed"
```

### 3. The full surface — inspecting a suspended handle's pending request, then a whole tree

```clojure
;; after a §10 approval request suspends the handle mid-turn:
(let [detail (rt/inspect runtime "root/boss.1/worker.1")]
  (:state detail)                    ; => "suspended"
  (:pending detail))                 ; => {:kind "approval" :prompt "…" :id "…" :data {...}}

;; enumerate the whole subtree under boss, tree order, root excluded
(rt/handles runtime "root/boss.1")
;; => [{:id "root/boss.1/worker.1" :state "suspended" :tokens 30 :inbox 0}]
```
