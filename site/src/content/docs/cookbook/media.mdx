<Aside type="tip" title="Why you need this">
Every media provider makes you write the same code twice: a start request, then a polling
loop that waits for the job, then a hunt through the response for the URL. Do it for image,
video and speech, in every language you ship, and do it again when you switch provider. With
Toolnexus a provider is a **JSON style file**: you call `image`, `video` and `speech` from your
code, and your agent gets `generate_image`, `generate_video` and `generate_speech` as tools.
Same engine, same polling, same results.
</Aside>

The recipe uses the shipped [a2e](https://a2e.ai) style,
`examples/media-styles/a2e.json`, which supports `image`, `video` and `speech`. It reads
`A2E_API_KEY` from the environment when it sends a request, and never logs it. Every a2e
verb is async: the engine starts the job and polls it for you. Measured live: an image takes
about 30 s, speech about 30 s, a 5-second video about 4 minutes. Pass `onProgress` if you want
to show that progress to someone. The full concept is on the
[Media generation](/toolnexus/media/) page.

<Aside type="caution">
a2e result URLs **expire** (images after about 3 days, audio after about 30). If you need
the file later, download it yourself. Toolnexus does not download yet.
</Aside>

## 1. Your code: image, then video, then speech

The video takes the image's URL as its starting frame. You chain the two calls by passing a
URL, nothing more.

Every verb returns the same shape: `files` (each `{type, mimeType, url}`), `status`, plus
`jobId` for async styles and `text` for `transcribe`. A failure is an error (an exception, a
`Result::Err`, an `{:error, msg}` tuple), and the message is the same in every language:
`job 66f… failed: <reason>`, `HTTP 401: <body>`, `image: argument "aspectRatio" not supported
by this style`.

<Aside>
A style only accepts the arguments it maps. a2e's `image` takes `prompt`, `width`, `height`
and `seed`, so passing `aspectRatio` is an error **before** any request is made. You never pay
for a call that would ignore your argument. For a provider parameter the normalised verbs
don't cover, pass `providerOptions` (`provider_options` in Python and Elixir,
`:provider-options` in Clojure). Its top-level keys are written over the request body last.
</Aside>

## 2. Your agent: the same verbs as tools

Give the toolkit the same `media`. The model now sees `generate_image`, `generate_video` and
`generate_speech`, with schemas that list only the arguments a2e accepts. When it calls
them, everything they produce lands in `RunResult.files`, in call order and tagged with the
tool name. The answer text never gets markup for them, so you decide how to show them.

A provider error never crashes the run. The tool returns `isError: true` with the same message
your code would have got, and the model sees it and can retry or explain. In the live a2e run, a
missing `negative_prompt` came back as `HTTP 400 …`. The fix was one line in the style's
`defaults`, with no code change.

`createToolkit({ media })` is shorthand for `toolkit.register(...media.tools())`. Media
tools register after A2A agent tools and before `extraTools`, and the first tool with a name
wins, as for every other source.

## 3. Show the files

`RunResult.files` is plain data, so each host renders it its own way:

- **Web.** `image/*` goes in an `<img>`, `video/*` in a `<video controls>`, `audio/*` in an `<audio controls>`.
- **WhatsApp / Telegram.** Send each URL as a media message, using `mimeType` to pick image, video or voice note.
- **CLI.** Print `from`, `mimeType` and the URL, or download it to disk (do this soon, because a2e URLs expire).

and exits 0, so it never touches the network in CI.
