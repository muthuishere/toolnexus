<Aside type="tip" title="Why you need this">
Not every model lives behind a URL. Yours might be an ONNX Runtime session, a
llama.cpp binding, a fine-tune loaded straight into your process, or a router you
wrote yourself. toolnexus never assumes a network: the same seam that lets you
supply a proxy lets you supply **the model itself**. Everything above it — the
tool-calling loop, MCP tools, skills, sub-agents, retries, memory — works
unchanged, because none of it knows whether a socket was involved.
</Aside>

A local OpenAI-compatible server — `llama-server`, Ollama, vLLM, LM Studio — is
just a `baseUrl`, so it needs no recipe. This page is about the case that does:
**the model runs inside your process and there is no server at all.**

## One option changes. Nothing else does.

The agent loop, tool calling, MCP servers and skills are untouched and never
learn that a model moved. You supply one thing: a **method that answers a
request**.

## The contract

Your method receives the request body and returns the response body, both in the
**OpenAI shape**. That is the entire interface — how you load or run the model is
your business, and this page deliberately says nothing about it.

**You receive** the assembled request:

```json
{
  "model": "local",
  "messages": [ {"role": "user", "content": "What is 2 + 3?"} ],
  "tools":    [ {"type": "function", "function": {"name": "add", "parameters": {}}} ]
}
```

**You must return** exactly one assistant message, either with `content` or with
`tool_calls` — never both — plus `usage`:

```json
{
  "choices": [{
    "index": 0,
    "message": {"role": "assistant", "content": "The answer is 5."},
    "finish_reason": "stop"
  }],
  "usage": {"prompt_tokens": 1, "completion_tokens": 1, "total_tokens": 2}
}
```

To call a tool, return `tool_calls` instead and set `finish_reason` to
`"tool_calls"`. `arguments` is a **JSON string**, not an object — that is the
OpenAI wire format, and the loop parses it:

```json
{"role": "assistant", "tool_calls": [
  {"id": "c1", "type": "function",
   "function": {"name": "add", "arguments": "{\"a\":2,\"b\":3}"}}
]}
```

The loop then runs the tool, appends the result, and calls you again. Returning
`content` ends the run.

<Aside type="note" title="If your model does not speak this">
Most local models do not. A Qwen-style model wants ChatML in and emits
`<tool_call>` tags out; a llama.cpp binding may want a prompt string. **That
translation belongs in your method**, not in the agent loop — which is exactly
why the seam is shaped as "a request in, a response out" rather than as a model
API.
</Aside>

## The seam, in every language

Each of these runs a full tool-calling turn — the model asks for `add`, the tool
executes, the model answers — with **zero sockets opened**. `generate` stands in
for your model; everything around it is the whole integration.

class LocalModel:
    def generate(self, messages, tools): ...   # → one assistant message

class LocalTransport:
    """THE SEAM: post() gets a dict and returns a dict — no JSON round trip."""
    def __init__(self, model): self.model = model

    def post(self, url, headers, payload, timeout):

        return {
            "choices": [{"index": 0, "message": message,

type LocalModel struct{}

func (m *LocalModel) Generate(messages []any, tools []any) map[string]any { /* → one message */ }

// THE SEAM: http.RoundTripper is a real interface, so no socket is opened.
type localRoundTripper struct{ model *LocalModel }

func (rt *localRoundTripper) RoundTrip(req *http.Request) (*http.Response, error) {
    var body map[string]any
    raw, _ := io.ReadAll(req.Body)
    _ = json.Unmarshal(raw, &body)
    msgs, _ := body["messages"].([]any)
    tools, _ := body["tools"].([]any)

    message := rt.model.Generate(msgs, tools)
    message["role"] = "assistant"
    finish := "stop"
    if _, ok := message["tool_calls"]; ok { finish = "tool_calls" }

    out, _ := json.Marshal(map[string]any{
        "choices": []any{map[string]any{"index": 0, "message": message, "finish_reason": finish}},
        "usage":   map[string]any{"prompt_tokens": 1, "completion_tokens": 1, "total_tokens": 2},
    })
    return &http.Response{StatusCode: 200, Body: io.NopCloser(bytes.NewReader(out)),
        Header: http.Header{"Content-Type": []string{"application/json"}}, Request: req}, nil
}

client := tn.CreateClient(tn.ClientOptions{
    BaseURL: "http://in-process.invalid", Style: tn.StyleOpenAI, Model: "local", APIKey: "unused",
    HTTPClient: &http.Client{Transport: &localRoundTripper{model: &LocalModel{}}},  // ← one line
})

// The JDK's HttpClient has no interceptor, so the seam is a subclass.
// Only send() is ever called by toolnexus — the rest are inert.
static final class LocalHttpClient extends HttpClient {
    private final LocalModel model;
    LocalHttpClient(LocalModel model) { this.model = model; }

    @Override @SuppressWarnings("unchecked")
    public <T> HttpResponse<T> send(HttpRequest req, HttpResponse.BodyHandler<T> handler) {
        String message = model.generate();                 // → one assistant message, as JSON
        String finish  = message.contains("tool_calls") ? "tool_calls" : "stop";
        String json = "{\"choices\":[{\"index\":0,\"message\":" + message
                + ",\"finish_reason\":\"" + finish + "\"}],"
                + "\"usage\":{\"prompt_tokens\":1,\"completion_tokens\":1,\"total_tokens\":2}}";
        return (HttpResponse<T>) new LocalResponse(req, json);
    }

    @Override public Optional<CookieHandler> cookieHandler() { return Optional.empty(); }
    @Override public Optional<Duration> connectTimeout()     { return Optional.empty(); }
    @Override public Redirect followRedirects()              { return Redirect.NEVER; }
    @Override public Optional<ProxySelector> proxy()         { return Optional.empty(); }
    @Override public SSLContext sslContext()       { throw new UnsupportedOperationException(); }
    @Override public SSLParameters sslParameters() { throw new UnsupportedOperationException(); }
    @Override public Optional<Authenticator> authenticator() { return Optional.empty(); }
    @Override public Version version()                       { return Version.HTTP_1_1; }
    @Override public Optional<Executor> executor()           { return Optional.empty(); }
    @Override public <T> CompletableFuture<HttpResponse<T>> sendAsync(
            HttpRequest r, HttpResponse.BodyHandler<T> h) {
        return CompletableFuture.completedFuture(send(r, h));
    }
    @Override public <T> CompletableFuture<HttpResponse<T>> sendAsync(
            HttpRequest r, HttpResponse.BodyHandler<T> h, HttpResponse.PushPromiseHandler<T> p) {
        return sendAsync(r, h);
    }
}

// A record covers the response side (statusCode/body/headers do the work).
record LocalResponse(HttpRequest req, String payload) implements HttpResponse<String> {
    @Override public int statusCode()  { return 200; }
    @Override public String body()     { return payload; }
    @Override public HttpRequest request() { return req; }
    @Override public HttpHeaders headers() {
        return HttpHeaders.of(Map.of("content-type", List.of("application/json")), (a, b) -> true);
    }
    @Override public Optional<HttpResponse<String>> previousResponse() { return Optional.empty(); }
    @Override public Optional<SSLSession> sslSession() { return Optional.empty(); }
    @Override public URI uri() { return req.uri(); }
    @Override public HttpClient.Version version() { return HttpClient.Version.HTTP_1_1; }
}

// THE SEAM: an HttpMessageHandler. No socket is opened.
private sealed class LocalHandler : HttpMessageHandler
{
    private readonly LocalModel _model;
    public LocalHandler(LocalModel model) => _model = model;

    protected override async Task<HttpResponseMessage> SendAsync(
        HttpRequestMessage request, CancellationToken cancellationToken)
    {
        var requestBody = request.Content is null
            ? "" : await request.Content.ReadAsStringAsync(cancellationToken);

        var message = _model.Generate(requestBody);      // → one assistant message, as JSON
        var finish  = message.Contains("tool_calls") ? "tool_calls" : "stop";
        var json = "{\"choices\":[{\"index\":0,\"message\":" + message
                 + ",\"finish_reason\":\"" + finish + "\"}],"
                 + "\"usage\":{\"prompt_tokens\":1,\"completion_tokens\":1,\"total_tokens\":2}}";

        return new HttpResponseMessage(HttpStatusCode.OK)
        {
            Content = new StringContent(json, Encoding.UTF8, "application/json"),
        };
    }
}

# THE SEAM: a one-arg function. req.body is an UN-MARSHALLED map and the
# response body goes back as a map — no JSON round trip for an in-process model.
local_transport = fn req ->
  message =
    LocalModel.generate(req.body["messages"], req.body["tools"])
    |> Map.put("role", "assistant")

  finish = if Map.has_key?(message, "tool_calls"), do: "tool_calls", else: "stop"

  {:ok,
   %{status: 200,
     headers: %{"content-type" => "application/json"},
     body: %{
       "choices" => [%{"index" => 0, "message" => message, "finish_reason" => finish}],
       "usage" => %{"prompt_tokens" => 1, "completion_tokens" => 1, "total_tokens" => 2}
     }}}
end

client =
  Toolnexus.Client.create(

One warning worth inheriting: **pick a model actually trained for tool calling.**
A 135M instruct model will hallucinate an answer rather than call, and no amount
of transport code fixes that.


## What crosses the seam, per port

The examples above are Go and Python, but the seam exists in every port — and
because each is idiomatic, the **body shape differs**. Spelled out so you do not
have to read the source to find out:

| Port | Seam | Request body you receive | Response body you return |
|------|------|--------------------------|--------------------------|
| JavaScript | `fetch` | `init.body` — a JSON **string** | a `Response` (JSON string) |
| Python | `http_transport` (`post`/`open`) | a **dict** | a **dict** |
| Go | `HTTPClient` (`http.RoundTripper`) | `req.Body` — **bytes** | `*http.Response` (bytes) |
| Java | `httpClient` (subclass `HttpClient`) | `HttpRequest` — **bytes** | `HttpResponse<String>` |
| C# | `HttpHandler` (`HttpMessageHandler`) | `HttpRequestMessage` — **bytes** | `HttpResponseMessage` |
| Elixir | `transport` (1-arg fn) | `req.body` — an **un-marshalled map** | a **map** |
| Clojure | `:http-client` (`(url headers body)`) | a JSON **string** | `{:status :headers :body}`, body a JSON string |

Python and Elixir hand you the body already parsed, so an in-process model there
pays **no serialization at all**. The other five hand you bytes, because that is
what their HTTP client hands them.

<Aside type="note" title="Streaming, honestly">
The recipes above implement the non-streaming path, which is what a tool-calling
loop uses. If you also want `runStream`, your seam must return an **incremental**
body — a buffered one produces the same final text and the same delta count as a
real stream, so a test asserting on content cannot tell them apart. Python's seam
splits this explicitly (`post` vs `open`); the others distinguish it by
`stream: true` in the request body.
</Aside>

## What you do **not** have to change

This is the part worth being explicit about: **you swap one option, and nothing
else in your setup moves.**

The seam is scoped to the LLM path on purpose. Your MCP servers, agent skills,
native and HTTP tools, built-ins and outbound A2A agents keep using their own
clients and keep working **exactly as they did against a hosted model** — you do
not re-register them, re-wire them, or run them in a special mode:

```ts
// The ONLY line that changes when you move from GPT-4o to a model in your process.
const client = createClient({
  baseUrl: "http://local.invalid", style: "openai", model: "local", apiKey: "unused",
  fetch: localFetch(new LocalModel()),   // ← this line, and nothing else
})

// Untouched. Still real MCP servers over stdio and HTTP, still real skills.
const toolkit = await createToolkit({
  mcpConfig: "./mcp.json",
  skillsDir: "./skills",
})
```

That separation is deliberate, and it is what makes a local model *useful* rather
than merely isolated. A model running in your process still needs to read files,
query GitHub, call your REST API and hand work to another agent — so the MCP
servers and HTTP tools **should** open their real connections. A seam that
silenced them along with the model would have turned a working agent into a
sandbox.

Run against the shared `examples/mcp.json` fixture, that is exactly what you get
— a socket-free model calling a real stdio MCP server it knows nothing about:

```
mcp status : {"example-remote":"disabled","everything":"connected"}
tools      : 24 | has everything_echo: true | has skill: true
text       : MCP replied: Echo: hello from a local model
toolCalls  : [ [ 'everything_echo', 'Echo: hello from a local model' ] ]
```

The MCP server was spawned, connected and called normally. The model never
opened a connection. Neither half knows about the other, which is the whole
design.

<Aside type="note" title="So it is not an 'offline mode' switch">
One consequence to be precise about: because tool sources keep their own clients,
an in-process model makes **model calls** socket-free, not the whole process. If
what you actually want is a fully hermetic test, that is a different job — reach
for the toolkit's own controls (`builtins: false`, `disableTools`, an empty
`mcp.json`) and choose which sources exist, rather than expecting the model seam
to mute them.
</Aside>
