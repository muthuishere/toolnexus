<Aside type="tip" title="Why you need this">
Not every model lives behind a URL. Yours might be an ONNX Runtime session, a
llama.cpp binding, a fine-tune loaded straight into your process, or a router you
wrote yourself. toolnexus never assumes a network: the same seam that lets you
supply a proxy lets you supply **the model itself**. Everything above it — the
tool-calling loop, MCP tools, skills, sub-agents, retries, memory — works
unchanged, because none of it knows whether a socket was involved.
</Aside>

A local OpenAI-compatible server — `llama-server`, Ollama, vLLM, LM Studio — is
just a `baseUrl`, so it needs no recipe. This page is about the case that does:
**the model runs inside your process and there is no server at all.**

## One option changes. Nothing else does.

```py
client = create_client(
    base_url="http://in-process.invalid", style="openai", model="qwen2.5-1.5b", api_key="unused",
    http_transport=OnnxTransport(model),   # ← this line, and nothing else
)
```

The agent loop, tool calling, MCP servers and skills are untouched and never
learn that a model moved.

<Aside type="caution" title="You are implementing a response shape, not a model API">
Your seam receives an **OpenAI-shaped request body** and must return an
**OpenAI-shaped response body** — `choices[0].message` with either `content` or
`tool_calls`, plus `usage`. If your model speaks something else (Qwen's ChatML
and `<tool_call>` tags, say), that translation is your transport's job. Keeping
it there is what keeps it out of the agent loop.
</Aside>

The transport is the whole integration — `post` receives the request body as a
**dict** and returns a **dict**, so an in-process model pays no serialization:

```python
class OnnxTransport:
    def __init__(self, model): self.model = model

    def post(self, url, headers, payload, timeout):
        prompt = to_chatml(payload.get("messages") or [], payload.get("tools"))
        raw = self.model.generate(prompt)
        message = to_openai_response(raw)          # <tool_call> -> OpenAI tool_calls
        return {
            "choices": [{"index": 0, "message": message,
                         "finish_reason": "tool_calls" if "tool_calls" in message else "stop"}],
            "usage": {"prompt_tokens": len(self.model.tok.encode(prompt).ids),
                      "completion_tokens": len(self.model.tok.encode(raw).ids),
                      "total_tokens": 0},
        }

    def open(self, url, headers, payload, timeout):
        raise NotImplementedError("non-streaming path only")
```

Dependencies are `onnxruntime`, `tokenizers` and `numpy` — deliberately **not**
`transformers`, so the chat template and tool-call parsing stay visible in the
example instead of hidden in a library.
</TabItem>

`http.RoundTripper` is a real interface, so the seam is an ordinary
`*http.Client` that simply never reaches the network:

```go
type localRoundTripper struct{ model *OnnxModel }

func (rt *localRoundTripper) RoundTrip(req *http.Request) (*http.Response, error) {
    var body map[string]any
    raw, _ := io.ReadAll(req.Body)
    _ = json.Unmarshal(raw, &body)

    text, promptTokens, completionTokens, err := rt.model.Generate(toChatML(body), 256)
    if err != nil { return nil, err }

    message := toOpenAIMessage(text)   // <tool_call> -> OpenAI tool_calls
    finish := "stop"
    if _, ok := message["tool_calls"]; ok { finish = "tool_calls" }
    out, _ := json.Marshal(map[string]any{
        "choices": []any{map[string]any{"index": 0, "message": message, "finish_reason": finish}},
        "usage":   map[string]any{"prompt_tokens": promptTokens, "completion_tokens": completionTokens,
                                  "total_tokens": promptTokens + completionTokens},
    })
    return &http.Response{StatusCode: 200, Body: io.NopCloser(bytes.NewReader(out)),
        Header: http.Header{"Content-Type": []string{"application/json"}}, Request: req}, nil
}

client := tn.CreateClient(tn.ClientOptions{
    BaseURL: "http://in-process.invalid", Style: tn.StyleOpenAI,
    Model: "qwen2.5-1.5b-instruct-onnx", APIKey: "unused",
    HTTPClient: &http.Client{Transport: &localRoundTripper{model: model}},
})
```

It is a **separate Go module** on purpose: in-process ONNX needs two native
artifacts, and toolnexus itself must not acquire them — a nested `go.mod` keeps
`go build ./...` in the library free of both.
</TabItem>

### Three things that will cost you an afternoon

Each of these was hit while building the examples, not anticipated:

1. **Pick a model actually trained for tool calling.** `SmolLM2-135M-Instruct`
   cannot do it — it hallucinates an answer instead of calling, prefill-forcing
   produces looping malformed JSON, and constrained scoring picks `get_weather`
   for *"what is 2 plus 3?"*. No amount of transport code fixes the model.
2. **Export with `--task text-generation-with-past`.** That flag is what emits
   the `past_key_values`/`present` pairs. Without the KV cache, generation is
   quadratic. After quantizing, delete the `model.onnx_data` left over from the
   fp32 export — the int8 graph is self-contained, and that file is 6.6 GB
   nothing reads.
3. **In Go, a pure-Go tokenizer will not do.** Qwen's pre-tokenizer regex uses a
   negative lookahead (`\s+(?!\S)`) that Go's RE2 engine cannot compile, so
   `sugarme/tokenizer` panics at load. The example uses `daulet/tokenizers`, a
   CGO binding to HuggingFace's Rust tokenizers. Separately, `onnxruntime_go`
   v1.33 needs ORT **≥ 1.29**, or it fails with
   `The requested API version [29] is not available`.


## What crosses the seam, per port

The examples above are Go and Python, but the seam exists in every port — and
because each is idiomatic, the **body shape differs**. Spelled out so you do not
have to read the source to find out:

| Port | Seam | Request body you receive | Response body you return |
|------|------|--------------------------|--------------------------|
| JavaScript | `fetch` | `init.body` — a JSON **string** | a `Response` (JSON string) |
| Python | `http_transport` (`post`/`open`) | a **dict** | a **dict** |
| Go | `HTTPClient` (`http.RoundTripper`) | `req.Body` — **bytes** | `*http.Response` (bytes) |
| Java | `httpClient` (subclass `HttpClient`) | `HttpRequest` — **bytes** | `HttpResponse<String>` |
| C# | `HttpHandler` (`HttpMessageHandler`) | `HttpRequestMessage` — **bytes** | `HttpResponseMessage` |
| Elixir | `transport` (1-arg fn) | `req.body` — an **un-marshalled map** | a **map** |
| Clojure | `:http-client` (`(url headers body)`) | a JSON **string** | `{:status :headers :body}`, body a JSON string |

Python and Elixir hand you the body already parsed, so an in-process model there
pays **no serialization at all**. The other five hand you bytes, because that is
what their HTTP client hands them.

<Aside type="note" title="Streaming, honestly">
The recipes above implement the non-streaming path, which is what a tool-calling
loop uses. If you also want `runStream`, your seam must return an **incremental**
body — a buffered one produces the same final text and the same delta count as a
real stream, so a test asserting on content cannot tell them apart. Python's seam
splits this explicitly (`post` vs `open`); the others distinguish it by
`stream: true` in the request body.
</Aside>

## What you do **not** have to change

This is the part worth being explicit about: **you swap one option, and nothing
else in your setup moves.**

The seam is scoped to the LLM path on purpose. Your MCP servers, agent skills,
native and HTTP tools, built-ins and outbound A2A agents keep using their own
clients and keep working **exactly as they did against a hosted model** — you do
not re-register them, re-wire them, or run them in a special mode:

```ts
// The ONLY line that changes when you move from GPT-4o to a model in your process.
const client = createClient({
  baseUrl: "http://local.invalid", style: "openai", model: "local", apiKey: "unused",
  fetch: localFetch(new LocalModel()),   // ← this line, and nothing else
})

// Untouched. Still real MCP servers over stdio and HTTP, still real skills.
const toolkit = await createToolkit({
  mcpConfig: "./mcp.json",
  skillsDir: "./skills",
})
```

That separation is deliberate, and it is what makes a local model *useful* rather
than merely isolated. A model running in your process still needs to read files,
query GitHub, call your REST API and hand work to another agent — so the MCP
servers and HTTP tools **should** open their real connections. A seam that
silenced them along with the model would have turned a working agent into a
sandbox.

Run against the shared `examples/mcp.json` fixture, that is exactly what you get
— a socket-free model calling a real stdio MCP server it knows nothing about:

```
mcp status : {"example-remote":"disabled","everything":"connected"}
tools      : 24 | has everything_echo: true | has skill: true
text       : MCP replied: Echo: hello from a local model
toolCalls  : [ [ 'everything_echo', 'Echo: hello from a local model' ] ]
```

The MCP server was spawned, connected and called normally. The model never
opened a connection. Neither half knows about the other, which is the whole
design.

<Aside type="note" title="So it is not an 'offline mode' switch">
One consequence to be precise about: because tool sources keep their own clients,
an in-process model makes **model calls** socket-free, not the whole process. If
what you actually want is a fully hermetic test, that is a different job — reach
for the toolkit's own controls (`builtins: false`, `disableTools`, an empty
`mcp.json`) and choose which sources exist, rather than expecting the model seam
to mute them.
</Aside>
