Your agent is halfway through a task and hits a wall only a person can clear: **approve a refund**,
**log into a bank**, **pick between two options**, **sign off on a risky action**. What should the
loop do — crash? Block a thread for six hours? Guess?

toolnexus gives you a fourth answer: **suspend**. Any tool can pause the loop, surface a `Request`,
and resume once it's answered — the same way in all seven ports.

## The one decision: can the human answer *now*, or *later*?

This is the whole mental model. Everything else follows from it.

| The answer arrives… | Give the client… | What `run()` does |
|---------------------|------------------|-------------------|
| **Now** — a person is right there, or a service resolves it inside the same request (seconds) | a **`waitFor`** host | Blocks on `waitFor`, feeds the answer back, runs on to `status: "done"`. The pause is invisible. |
| **Later** — minutes to days later, maybe in another process, after the web request already returned | **no `waitFor`** | Returns `status: "pending"` with the `Request`. You persist it and come back through the answer-carrying entry point — which is **`golang`-only today**, so read [Scenario 3](#scenario-3--answer-later-in-chat-the-durable-halt) before you build on it. |

Same primitive, two postures. Pick by *when the human answers*, not by what you're asking.

## The primitive

A tool suspends by returning `pending(Request)`. The client resolves it to an `Answer`.

```ts
// A tool returns this instead of a result:
pending({ kind: "question", prompt: "Ship it?", data: { questions: [...] } })

// Request  → { id, kind, prompt, url?, data?, expiresAt? }
// Answer   → { id, ok, data?, reason? }
```

`ok: false` declines; the optional `reason` (`"declined"` | `"cancelled"` | `"expired"`) is
advisory — the loop always branches on `ok`. `kind` is just data: `"question"`, `"input"`,
`"authorization"`. There is no auth subsystem — [authorization is the same primitive](#scenario-2--login--oauth-wait-authorization) with a `url`.

<Aside type="tip">
A suspension is nothing more than a **tool's return value**. Any tool — one that calls an external
API, checks a policy, or just needs a human — can decide mid-execution that it can't finish alone and
return `pending(...)`. It's not a separate mechanism bolted onto the loop.
</Aside>

## Scenario 1 — Approval gate (answer *now*)

An agent is about to do something irreversible — issue a refund, delete a resource, send money.
You want a human to approve first, and they're on the other end of a CLI or a chat you can await.
Give the client a **`waitFor`**: the loop pauses, asks, and resumes to `done` in one call.

<Tabs syncKey="lang">
<TabItem label="JavaScript">
```ts
import { createClient, type Answer, type Request } from "toolnexus"
import { createInterface } from "node:readline/promises"

const rl = createInterface({ input: process.stdin, output: process.stdout })

const client = createClient({
  baseUrl, style: "openai", model,
  // Called whenever a tool suspends. Read the operator's decision straight off the terminal.
  waitFor: async (req: Request): Promise<Answer> => {
    const line = await rl.question(`${req.prompt} [y/N] `)
    return { id: req.id, ok: line.trim().toLowerCase() === "y" }   // ok:false → loop tells the model it was declined
  },
})

const result = await client.run("Refund order #4021 if policy allows.", { toolkit })
// result.status === "done" — the refund tool ran only after you typed y
```

## Scenario 2 — Login / OAuth wait (`authorization`)

A tool needs the user to authenticate — connect a bank, grant an OAuth scope, click a consent
link. There's no auth subsystem: the tool returns a suspension whose `kind` is `"authorization"`
and whose `url` is where the human goes. Your `waitFor` delivers that link (open a browser, text it
to a channel) and returns once the world has changed — the session is now valid, so the retried
tool just succeeds.

```ts
import { defineTool, authRequired } from "toolnexus"

let authed = false
const getBalance = defineTool({
  name: "get_balance",
  description: "Return the account balance. Requires login first.",
  inputSchema: { type: "object", properties: {}, additionalProperties: false },
  run: (_args, ctx) =>
    authed
      ? `balance: ₹67,417`
      : authRequired("https://bank.example/login?t=abc", "Log in to view your balance"),
})

const client = createClient({
  baseUrl, style: "openai", model,
  waitFor: async (req) => {
    await deliverLink(req.url!)   // open a browser, OR text the link to #ops, OR forward over A2A
    authed = true                 // the world changed out-of-band; the retry now succeeds
    return { id: req.id, ok: true }   // kind:"authorization" ignores answer.data — the session is enough
  },
})
```

<Aside type="note">
`authRequired(url, prompt)` is a one-liner over the same primitive — it returns
`pending({ kind: "authorization", url, prompt })`. The **same shape works in all seven ports**;
only the surface syntax differs. Nothing here is special-cased for auth.
</Aside>

## Scenario 3 — Answer later, in chat (the durable halt)

This is the one most frameworks can't do. The agent asks a question your user **won't answer for
hours** — it posts to a Slack thread, or an email, and the web request that started the run has to
return *now*. There's no thread to block. So you give the client **no `waitFor`**: `run()` halts and
hands you the `Request`. You persist it, post it, and let the HTTP request finish.

**Getting back in is where you have to choose a posture, and the two are not equally portable:**

| posture | how the answer gets back in | ports |
|---|---|---|
| **A — deferred `waitFor`** | the run stays alive; its `waitFor` awaits a promise/future/channel that your reply handler resolves | **all seven** |
| **B — durable halt + answer-carrying resume** | the process may exit; you come back through `runWithAnswer` / `askWithAnswer` carrying the `Answer` | **`golang` only today** — a preview, outside the conformance contract |

<Aside type="caution" title="Replaying the conversation is NOT a resume">
Calling `ask` again on the same conversation id after a halt **does not resume anything**. The
stored transcript already contains the halted call's placeholder result, so the tool is never
re-invoked, your `waitFor` is never called, and the run returns `status: "done"` with the model
answering off the placeholder — a healthy-looking log and a dropped human reply. (An earlier
version of this page documented exactly that flow. It was wrong; see
[ADR 0026](https://github.com/muthuishere/toolnexus/blob/main/docs/adr/0026-the-answer-payload-contract.md).)
The only durable way back in is the answer-carrying entry point, posture B.
</Aside>

**Phase 2, posture A — a `waitFor` that *waits* (works in all seven ports):**

The run never ended. Its `waitFor` parks on a promise / future / channel / process mailbox, and your
chat webhook resolves it whenever the reply lands. Because this is the inline path, the **whole
`Answer` reaches the tool** as `ctx.answer` — no key is reserved, so `answers`, `value` or `text`
all work, and the suspended tool re-runs exactly once with the answer in hand.

<Tabs syncKey="lang">
<TabItem label="JavaScript">
```ts
const parked = new Map<string, (a: Answer) => void>()

const client = createClient({
  baseUrl, style: "openai", model,
  waitFor: (req: Request) => new Promise<Answer>((resolve) => {
    slack.post(channel, req.prompt)          // ask, out of band
    parked.set(req.id, resolve)               // …and park the run on the reply
  }),
})

// your Slack webhook, minutes or hours later — a different handler, same process:
export function onSlackReply(requestId: string, reply: string) {
  parked.get(requestId)?.({ id: requestId, ok: true, data: { answers: [reply] } })
  parked.delete(requestId)
}

const done = await client.run(prompt, { toolkit })   // settles when the human answers
// done.status === "done" — the tool re-ran with ctx.answer.data = { answers: [reply] }
```
</TabItem>

<Aside type="note" title="What posture A costs you">
The process has to stay up. A parked `waitFor` is cheap — no thread is spinning, and in every port
it is the ordinary idiom for "await a callback" — but a deploy or a crash loses the parked run.
Give your `waitFor` a timeout and return `ok: false` when it expires; the loop feeds the model a
`declined/expired: <prompt>` result and carries on rather than hanging.
</Aside>

**Phase 2, posture B — the answer-carrying entry point (`golang` only, a preview):**

Survives a restart: phase 1 can run on one machine and phase 2 on another, a day later, because
`Request` and `Answer` are plain serializable data. This entry point exists **only in `golang`
today** and is explicitly outside the §0 conformance contract — `js`, `python`, `java`, `csharp`,
`elixir` and `clojure` can raise the durable halt but have no way back in yet, which is why posture
A is the portable answer.

```go
// A different process, the next day. You hold the persisted Request and the human's reply.
req := db.LoadRequest(conversationID)

done, err := c.AskWithAnswer(ctx, tk, conversationID, req,
    toolnexus.AnswerOutput(req.ID, reply))   // the typed constructor — do not hand-build the map
if err != nil {
    // e.g. the answer echoed the wrong id, or carried no determinable result:
    // an ERROR TO YOU, never a fabricated tool result handed to the model.
}
// done.Status == "done"
```

<Aside type="caution" title="`Answer.data` has reserved keys on this path — and only this path">
Posture B reads exactly two keys: **`results`** (`[{ id, output, isError }]`, one entry per
outstanding call) and, as a single-call shorthand, **`output`** (a string) with optional
`isError`. They are **string-keyed and identical in every port** — not atoms, not keywords, not
idiomatic-cased. Any other shape (`{"answers": […]}`, `{"value": "staging"}`) is **not** a
recognised payload, and `ok: true` with no determinable result is an error returned to you.
Use the `AnswerOutput` / `RelayAnswer` constructors and you never have to know this — and
`AnswerDeclined(id, reason)` when the human said no, which is a resolution (`ok: false` plus a
reason), not an error. All three ship in every port, including the six without a durable resume.

One more asymmetry worth knowing before you build on it: posture B splices your `output` into the
transcript as the call's result — the tool is **not** re-executed and never sees `ctx.answer`,
unlike posture A. Making a non-relay durable resume re-execute the tool is deferred to its own
change; until then, do not assume a tool's post-resume branch runs on this path.
</Aside>

<Aside type="note" title="One contract, two postures">
`Request` and `Answer` are **plain serializable data** — no live handle, no open socket — which is
what lets posture B cross a process boundary at all. The durable halt and the in-process `waitFor`
are the *same contract*; the difference is who is still holding the run when the answer arrives.
Posture A keeps the run; posture B persists the request and comes back through the answer-carrying
entry point, which today exists only in `golang`.

Whichever you pick: **a resumed turn replays from its pre-turn checkpoint, so every tool that ran
in that turn runs again** — and on the inline path the suspended tool is re-executed by design.
Tools reachable in a suspendable turn must be idempotent, or guarded by you.
</Aside>

## The `question` tool

You don't have to write a suspending tool to use any of this. The built-in **`question`** tool
suspends to ask the user structured questions and resumes with their answers — the same
sync-or-durable fork applies. It's how the agent asks *you* something mid-run without any custom code.

## MCP elicitation bridge

MCP servers can send a reverse request — `elicitation/create` — mid tool-call, asking the client
to collect input. toolnexus **bridges that onto the same primitive**: a form request maps to
`kind: "input"` (with the server's schema in `data.schema`), a URL request maps to
`kind: "authorization"`. Your single `waitFor` answers both your own agent's questions and any MCP
server's elicitations — one human-in-the-loop surface for everything. The capability is advertised
to servers only when a `waitFor` is present.

## Guarantees

- A suspension is **never** counted as a tool error — the loop emits `pending`, not `isError`, so
  error-rate metrics and circuit-breakers don't trip on a human wait.
- If several tools suspend at once with no `waitFor`, the **first in tool-call order** is
  surfaced — deterministically, with no transcript leak — in both the non-streaming and streaming
  loops.
- Streaming emits a `{ type: "pending", request }` event *before* `waitFor` runs, so a channel
  handler can push the link the instant the agent asks.

<Aside type="note">
This layer shipped byte-identical across JavaScript, Python, Go, Java, C#, Elixir and Clojure. The A2A fulfilment
path maps a suspended run to the A2A `input-required` state, so a *served* toolnexus agent can ask
its caller a question too.
</Aside>
